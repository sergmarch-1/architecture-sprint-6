Требования бизнеса:
1. RTO — 45 мин., RPO — 15 мин, доступность приложения = 99,9%;
2. обеспечить бесперебойную работу сервиса 24/7;
3. Обеспечить одинаковое время загрузки страниц для пользователей из разных регионов.

*Стратегия масштабирования и отказоустойчивости*

Описание основных компонентов целевой архитектуры:

-> Kubernetes-кластеры в 3-х зонах доступности (ЦОД): Москва, Новосибирск, Хабаровск (на данный момент, такие ЦОД имеются у одного провайдера в РФ - Ростелеком)
-> Глобальный балансировщик нагрузки для распределения трафика между зонами
-> Patroni Primary-кластер (Msk) + Standby Cluster (Nsk) + Standby Cluster (Khv). Standby-кластеры имеют только read replica.
-> HAProxy для балансировки трафика внутри кластера и перенаправления CUD операций из Standby в Primary.
-> Patroni API - для того, чтобы HAProxy знал, где находится актуальный Primary
-> Etcd в каждом кластере для координации и хранения состояния, а также для выбора нового Primary через консенсус. 
-> Горизонтальное масштабирование read-реплик (HPA) по RPS через Prometheus 


Вертикальное масштабирование (VPA) в данном случае не лучший вариант, т.к. задача - обеспечить бесперебойную работу сервиса, а VPA требует перезапуска пода. 
В свою очередь, горизонтальное масшатибрование (HPA) c Cluster Autoscaler для автоматического регулирования количества подов, позволит динамически добавлять мощности и лучше работает в распределенной среде с несколькими ЦОД.

RPS - кастомная метрика, для её использования в целях масштабирования системы необходимо настроить источник этой метрики. Эту функцию будет выполнять адаптер к системе мониторинга Prometheus.

Развертывание в дополнительных ЦОД позволит как ускорить получение информации пользователям из Сибири и Дальнего Востока, так и получить отказоустойчивость на уровне ЦОД.

*Фейловер стратегия и балансировка нагрузки*

Global Load Balancer (GLB) — определяет ближайший для пользователя ЦОД и направляет туда все запросы.
При выходе из строя ЦОД - трафик будет перенаправляться на доступные ЦОД так же при помощи GLB.

Стратегия "Active-Active" - потоковая репликация данных от Primary ноды ко всем остальным нодам во всех кластерах.

HAProxy - распределяет трафик на уровне кластера
Каждая нода Patroni периодически проверяет состояние кластера через etcd
При нарушении работы кластера - Patroni (etcd) автоматически назначит новый Primary узел в другом кластере и обновит конфигурацию всех HAProxy через PAtroni API
При failover master ноды -  Patroni выбирает лучшую реплику и она становится Primary

*Шардирование*

Шардирование данных core-db увеличит сложность архитектуры, а польза от этого неочевидна, тк данные по тарифам и заявкам одинаковые для регионов.
Можно рассмотреть геораспределенное шардирование client-info db, но только в случае явных проблем с производительностью этих баз.
